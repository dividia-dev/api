Overview

The ScaleWatcher Cloud API provides programmatic access to your scale transaction data, events, alerts, and user information. All API requests are made over HTTPS.

Base URL
https://api.cloud.dividia.net/sw/api

Quick Start

  1. Authenticate - POST to /sw/api/auth with your email and password
  2. Get your token - The response includes a JWT token valid for 30 days
  3. Select a site - Use the serial from your available sites
  4. Make requests - Include the token in the Authorization header

Authentication

All API requests (except /auth) require authentication via a Bearer token in the HTTP header:

Authorization: Bearer <your-api-token>

Getting a Token

Obtain a token by authenticating with your ScaleWatcher credentials:

// Request
POST /sw/api/auth
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "your-password"
}

// Response
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "user": {
    "id": 123,
    "email": "user@example.com",
    "name": "John Doe"
  },
  "sites": {
    "count": 2,
    "data": [...]
  }
}
Token Expiration
Tokens are valid for 30 days. After expiration, you must authenticate again to obtain a new token.
API Access Required
API access must be enabled for your account by a Dividia administrator. If you receive a 403 error indicating no API access, contact support@dividia.net or call 817-288-1040.

GET /sw/api/transactions/metrics

Aggregate counts and duration statistics (min / max / average) for transactions matching the supplied filters. Accepts every filter /sw/api/transactions accepts (including pass-through kv), plus groupBy to slice by time bucket or dimension.

Completed transactions only. count here excludes in-progress flows, so on an active site it is lower than the raw row count from /sw/api/transactions for the same filters.

Required Parameters

ParameterTypeDescription
serialintegerSite serial number

Optional Filters

ParameterTypeDescription
groupByenumOne of daily, hourly, carrier, customer, product, scale. Omit for a single summary row.
Plus all filters from /sw/api/transactions (date range, scale, lpn, truck, ticket, pass-through kv) — except scaleId/locationId, which are not accepted here (filter /transactions instead).

Response Fields

FieldTypeDescription
countintegerNumber of completed transactions
facilityDurationMin/Max/AvgintegerFacility duration stats (seconds)
scaleDurationMin/Max/AvgintegerOn-scale duration stats (seconds)
waitDurationMin/Max/AvgintegerWait duration stats (seconds)
datedateBucket date (when groupBy=daily)
hourstringBucket hour (when groupBy=hourly)
carrier / customer / product / scalevariesThe dimension value (when grouping by that dimension)

Example

curl "https://api.cloud.dividia.net/sw/api/transactions/metrics?serial=248&startDate=2024-01-01&endDate=2024-01-31&groupBy=carrier" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..."

GET /sw/api/events/keys

List the distinct metadata field names seen in event data (and one level under data.ticket for TicketReceived) at a site. Use this to discover valid pass-through key/value filter keys (customer, product, carrier, truck, etc.) for /sw/api/events, /transactions, and /transactions/pdf.

Searching by ticket fields. There is no separate "tickets" endpoint. To find records by customer, product, carrier, etc., pass them as pass-through key/value filters on /sw/api/events or /sw/api/transactions (e.g. ?name=TicketReceived&customer=ACME). This endpoint tells you which keys exist for a site.

Parameters

ParameterTypeDescription
serialintegerSite serial number
eventNamestringNarrow to keys seen in specific event types (comma-list, max 20).
categoryenumalert / non-alert narrowing.
date / startDate+endDate / sincedateRestrict the discovery window.

Example

curl "https://api.cloud.dividia.net/sw/api/events/keys?serial=248&eventName=TicketReceived" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..."

Command Cloud identifiers (scaleId, locationId)

If your tickets reach Dividia through a Command Cloud webhook integration, every transaction, event, and alert carries the two identifiers you sent — alongside Dividia's own serial and scale — so you can read and filter your data in your own terms.

FieldTypeWhat it is
scaleIdstringYour Command Cloud scale identifier, matched byte-for-byte (case- and punctuation-sensitive, e.g. IQ-001:A). Dividia maps it to a physical scale lane internally.
locationIdstringYour Command Cloud location.id for the site — maps to Dividia's serial. Also exposed per-site on /sw/api/sites.

Both are null on records that did not originate from Command Cloud. Where present they are accepted as exact-match filters on /sw/api/transactions, /sw/api/events, and /sw/api/alerts (?scaleId=…&locationId=…). They are not accepted on /sw/api/transactions/metrics — filter /transactions instead.

Sending tickets to Dividia? The webhook payload, headers, signing, and responses are documented in the Command Cloud webhook guide.

Response Format

All successful responses return JSON with a consistent structure:

{
  "page": 1,           // Current page number
  "pageSize": 25,       // Results per page
  "total": 1250,        // Total results available
  "count": 25,          // Results in this response
  "data": [...]         // Array of result objects
}

Date/Time Format & Timezones

Date parameters must be specified in YYYY-MM-DD format and are interpreted in the site's local timezone.

All timestamps in responses are ISO 8601 strings with the site's UTC offset embedded, so any standard date parser handles them without needing to know the timezone separately:

"2024-01-15T14:30:00-06:00"

Each row also includes a tzOffset field indicating the site's offset from UTC in whole hours (e.g., -6 for CST, -5 for CDT).

Timezone Note
Data is stored in UTC and converted to the site's local timezone for both filtering and response output. This ensures consistent date boundaries regardless of the API caller's location.

Image URLs

Event and alert images are returned as full URLs:

"https://api.cloud.dividia.net/uploads/scalewatcher/api/248/2024/01/15/image.jpg"

Error Handling

Error responses include a structured error object:

{
  "error": {
    "code": 400,
    "type": "BadRequest",
    "message": "Invalid 'startDate' value"
  }
}
