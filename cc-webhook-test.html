Fire a real request against staging (curl)

The sandbox above verifies locally. This actually POSTs to staging and returns our real response. Run it in a terminal (needs node + curl) — paste your signing secret first.

SECRET='whsec_...'                                  # paste the signing secret
CUSTOMER_ID='c8f7001c-b3a1-4744-bf30-c6296d0edb51'  # your Dividia-Customer-Id
BASE='https://api-staging.cloud.dividia.net'

# node signs (same HMAC our endpoint verifies); 4 values -> shell vars
{ read -r WID; read -r WTS; read -r SIG; read -r BODY; } < <(SECRET="$SECRET" node -e '
  const crypto = require("crypto");
  const secret = process.env.SECRET.replace(/^whsec_/, "");
  const ts = Math.floor(Date.now()/1000).toString();
  const id = "msg-" + ts;
  const body = JSON.stringify({ guid: "evt-"+ts, ticket: "1001", locationId: "LOC-1",
    locationName: "North Plant", scale: "1", timestamp: new Date().toISOString() });
  const sig = "v1," + crypto.createHmac("sha256", Buffer.from(secret,"base64"))
    .update(id+"."+ts+"."+body).digest("base64");
  console.log(id); console.log(ts); console.log(sig); console.log(body);
')

curl -sS -w '\nHTTP %{http_code}\n' -X POST "$BASE/sw/webhooks/cc" \
  -H 'Content-Type: application/json' \
  -H "Dividia-Customer-Id: $CUSTOMER_ID" \
  -H "webhook-id: $WID" -H "webhook-timestamp: $WTS" -H "webhook-signature: $SIG" \
  --data "$BODY"
Expected: HTTP 200 with {"status":"fallback"} — the ticket is stored as a cloud-only transaction (the test site has no NVR connected). This request has been validated against staging.

How it works

1 How it works

You POST the ticket JSON to our endpoint on each ticket creation, signed with a shared secret so we can verify origin and integrity.

YOU
Ticket created
A new ticket is created
→
YOU
Sign & POST
HMAC-SHA256 over the body, signature in a header
→
US
Verify
Look up the customer by header, recompute the signature; reject if it doesn't match
→
US
Ack + process
Return 200 immediately, then capture images from the on-site cameras
Why a signature and not a login? A webhook is server-to-server — there's no user session to authenticate. The shared secret proves both origin (only you and we hold it) and integrity (any change to the body breaks the signature), without ever putting a credential on the wire.
The payload

2 The payload we expect

One JSON object per created ticket. The six required fields are top-level; any additional ticket fields go in a data object (key/value JSON), which we store and return as-is.

{
  "guid":         "123e4567-e89b-12d3-a456-426614174000",   // per-delivery id
  "ticket":       "1001",                  // ticket number
  "locationId":   "site-123",               // site / plant — routes to the right location
  "locationName": "North Plant",            // display only
  "scale":        "2",                     // scale / lane
  "timestamp":    "2026-08-11T14:03:22Z",    // when the ticket was created (ISO-8601 UTC)
  "data": {                            // optional — additional ticket fields, key/value JSON
    "truck": "T-14", "material": "57 stone", "netWeight": 42980
  }
}
FieldPurpose
guidThe per-delivery id — constant across retries of the same delivery. This is what we de-duplicate on, so send the same guid when you retry.
ticketThe ticket number — indexed for search, and the anchor we key the on-site camera images to.
locationIdWhich site/plant — how we route the event to the right location.
locationNameDisplay only.
scaleWhich scale/lane at that site.
timestampWhen the ticket was created (ISO-8601 UTC).
dataOptional. Any additional ticket fields, as a key/value JSON object — stored and returned as-is, never parsed. Keeps your custom fields from colliding with the reserved ones.
Create-only. Every delivery represents a newly created ticket, so there is no type field and no separate update or delete events.
Signing

3 Signing

Sign each request with HMAC-SHA256 using the Standard Webhooks scheme. The headers and steps below are what our endpoint verifies.

Identifying the customer

Every customer posts to the same URL — POST /sw/webhooks/cc. You tell us which customer a delivery belongs to with a single request header:

Header
Dividia-Customer-Id: <uuid> — the customer's public id.
Who mints it
We do — we generate the customer id (and that customer's signing secret) and send them to you securely.
How we use it
We look up the customer by this header to know which secret to verify the signature with. Nothing customer-specific goes in the URL.

The shared secret

A random string both sides hold. It never travels over the wire; only the signature derived from it does. Format is whsec_ followed by a base64 value, e.g. whsec_c2VjcmV0LWtleS4uLg==.

Scope
One secret per customer.
Who mints it
We do — we generate the secret per customer and send it to you securely (along with that customer's Dividia-Customer-Id).
Rotation
Coordinated out-of-band (an email or a shared secrets vault — there's no auto-notify). During a changeover we accept both your current and new secret, so you can switch your sender over without dropping deliveries.

How a request is signed (3 steps)

For each POST you send three signing headers and sign a specific string:

// 1. Build the "signed content" string:  id . timestamp . rawBody
signedContent = "{webhook-id}" + "." + "{webhook-timestamp}" + "." + rawRequestBody

// 2. HMAC-SHA256 it with the base64-decoded secret, then base64 the result
secretBytes = base64_decode( secret without the "whsec_" prefix )
signature   = base64( HMAC_SHA256( secretBytes, signedContent ) )

// 3. Send these headers (signature is prefixed with the version "v1,")
webhook-id:        msg_2f8a...        // your unique delivery id
webhook-timestamp: 1754838245        // unix seconds
webhook-signature: v1,g30x...
Why sign id.timestamp.body and not just the body? Binding the timestamp into the signature is what enables replay protection — we reject anything whose timestamp is outside a ±5 minute window, so a captured request can't be replayed later. Binding the id lets us de-duplicate retries safely.
We verify over the exact raw bytes you sent — so serialize your JSON once and sign that exact string. Re-serializing (different key order or spacing) after signing will change the bytes and break verification.
Responses

5 What our responses mean

StatusMeaningShould you retry?
200 delivered / acceptedVerified and accepted.No
200 duplicateWe've already processed this delivery id — safely ignored.No
401Missing headers, unknown Dividia-Customer-Id, bad signature, or a timestamp outside the ±5 min window.Yes (fix header / signing / clock)
429Rate limited.Yes, after a short backoff
5xxOur side had a problem.Yes
Why we ack 200 fast, then process: we verify and immediately return 200 so your delivery queue doesn't back up, then do the heavier work (storage, on-site image capture) afterward. Send at-least-once with retries on any non-2xx — our de-duplication makes the occasional duplicate harmless.
What we do

6 What happens on our end

  • 1
    Identify the customer from the Dividia-Customer-Id header, then verify the signature over the raw body with that customer's secret. Anything that fails is rejected with a 401 before we touch a database.
  • 2
    De-duplicate on the delivery id, so retries are safe.
  • 3
    Store the ticket against the customer and site.
  • 4
    Capture images from the configured on-site cameras at that location and scale, keyed to the ticket number.
What we need

7 What we need from you to go live

What we need to configure your integration:

  • 1
    Confirm your sender can do the above — POST to the single /sw/webhooks/cc URL, send the Dividia-Customer-Id header, and sign with the Standard Webhooks HMAC-SHA256 headers.
  • 2
    Delivery & retries — at-least-once with retries on non-2xx is ideal; send the same guid on retries so our de-duplication works.
  • 3
    (Optional) your sender's source IPs, if you'd like us to allowlist them for extra defense.
Reference sender

8 Reference sender

Copy-paste signer you can run from a terminal or your backend once we've exchanged a customer id and secret. This produces the same output as the tester above.

Node.js

const crypto = require('crypto');

const SECRET = 'whsec_...';                 // the shared secret we exchanged
const CUSTOMER_ID = '123e4567-e89b-12d3-a456-426614174000';   // your Dividia-Customer-Id
const URL_ = 'https://api.cloud.dividia.net/sw/webhooks/cc';      // same URL for every customer

const body = JSON.stringify({
  guid: crypto.randomUUID(),
  ticket: '1001',
  locationId: 'site-123',
  locationName: 'North Plant',
  scale: '2',
  timestamp: new Date().toISOString()
});

const id = 'msg_' + Date.now();
const ts = Math.floor(Date.now() / 1000).toString();
const secretBytes = Buffer.from(SECRET.replace('whsec_', ''), 'base64');
const signature = crypto.createHmac('sha256', secretBytes)
                       .update(`${id}.${ts}.${body}`).digest('base64');

fetch(URL_, { method: 'POST', headers: {
  'Content-Type': 'application/json',
  'Dividia-Customer-Id': CUSTOMER_ID,
  'webhook-id': id, 'webhook-timestamp': ts, 'webhook-signature': `v1,${signature}`
}, body });

Python

import hmac, hashlib, base64, time, json, uuid, urllib.request

SECRET = 'whsec_...'
CUSTOMER_ID = '123e4567-e89b-12d3-a456-426614174000'
URL_ = 'https://api.cloud.dividia.net/sw/webhooks/cc'

body = json.dumps({'guid': str(uuid.uuid4()),
  'ticket': '1001', 'locationId': 'site-123',
  'locationName': 'North Plant', 'scale': '2',
  'timestamp': '2026-08-11T14:03:22Z'})

mid = 'msg_' + str(int(time.time()*1000))
ts  = str(int(time.time()))
secret_bytes = base64.b64decode(SECRET.split('_',1)[1])
sig = base64.b64encode(hmac.new(secret_bytes, f"{mid}.{ts}.{body}".encode(), hashlib.sha256).digest()).decode()

req = urllib.request.Request(URL_,
  data=body.encode(), headers={'Content-Type':'application/json',
  'Dividia-Customer-Id': CUSTOMER_ID,
  'webhook-id':mid, 'webhook-timestamp':ts, 'webhook-signature':f'v1,{sig}'})
urllib.request.urlopen(req)
